# 第一届 AI 全栈黑客松赛题速查

用途：以后优先读取本文，不再反复解析原始 PDF。本文是赛题要求、评分点、执行优先级和本项目技术路线的快速调用版。

## 1. 赛题一句话

开发一个“学科知识整合智能体”：对多本教材进行知识整合，构建可视化知识图谱，识别跨教材重复/互补/缺失内容，将多本教材压缩成不超过原始体量 30% 的精华版本，并基于整合后的知识库做带引用来源的 RAG 精准问答。

比赛时长：5 小时。

核心场景：
- 学生：减少重复阅读，提高学习效率。
- 教师：降低备课和教材对比成本。
- 教学管理者：获得课程整合依据，重点是课时压缩与教学主干提炼。

我们的产品原则：
- 主干优先：定义、关键关系、学习顺序、必要公式/方法必须保留。
- 细节降级：具体案例、重复解释、长篇背景不展开，只保留“一句话关键词 + 来源索引”。
- 删除可追溯：被 remove 的内容不是消失，而是降级到索引/RAG 可检索来源，避免教学完整性被质疑。

## 2. 官方任务目标

系统需要能够：
1. 自动加载多本教材，支持多格式。
2. 为每本教材构建知识图谱并可视化。
3. 跨教材识别知识点重叠、互补与缺失。
4. 将多本教材内容整合压缩到不超过原始体量 30% 的精华版本。
5. 基于整合后的知识库进行 RAG 精准问答，必须引用原文来源。
6. 自主设计 Agent 架构并提交架构说明文档。
7. 通过与学科教师的多轮对话，迭代优化整合方案。

## 3. 官方必须功能 P0

### 3.1 多格式教材加载与解析

必须支持：
- PDF
- Markdown
- TXT

建议支持：
- Word .docx

可选支持：
- Excel

验收点：
- 前端有上传区，支持拖拽/点击选择/批量上传。
- 上传后显示文件名、格式、大小、解析状态。
- 解析输出统一结构：textbook_id、filename、title、total_pages、total_chars、chapters。
- PDF 解析要识别章节结构，过滤页眉页脚，跳过图表区，大文件逐页处理。

### 3.2 单本教材知识图谱构建与可视化

每章调用 LLM 或规则抽取核心知识点：
- 概念
- 定理
- 方法
- 现象

知识点 schema：
- id
- name
- definition
- category
- chapter
- page
- source_text

关系类型至少实现四类中的三类：
- prerequisite：前置依赖
- parallel：并列关系
- contains：包含关系
- applies_to：应用关系

验收点：
- 选择一本教材后，系统能生成 JSON 节点和边列表。
- 前端能以可视化图谱展示。

### 3.3 知识图谱交互

必须支持：
- 点击节点查看详细信息：名称、定义、章节、原文出处。
- 多本教材加载后，节点大小或颜色深浅反映出现频次。
- 不同教材来源用不同颜色区分。
- 支持缩放、拖拽画布、拖拽节点。

建议支持：
- 搜索知识点并高亮。

推荐技术：D3.js、ECharts、Cytoscape.js、AntV G6。我们优先用 Cytoscape.js 或 ECharts。

### 3.4 跨教材知识图谱整合

这是赛题核心难点。

要求：
- 合并多本教材知识图谱。
- 识别不同教材中描述同一概念的知识点，即使措辞不同。
- 至少实现一种对齐算法：
  - Embedding 相似度。
  - LLM 判断等价。
  - 两者结合。
- 对重复知识点输出整合决策。

决策类型：
- merge：合并重复。
- keep：保留唯一或必要内容。
- remove：删除冗余。

整合决策 schema：
- decision_id
- action
- affected_nodes
- result_node
- reason
- confidence

压缩要求：
- 整合后保留内容总字数不超过原始总字数 30%。
- 前端展示原始总字数、整合后字数、压缩比。

验收点：
- 加载 2 本以上教材后，系统能自动识别重复知识点。
- 输出整合决策列表。
- 压缩比不超过 30%。

### 3.5 RAG 精准问答

不是普通聊天，必须有据可查。

RAG pipeline：
1. Chunking：每本教材正文拆成 chunk，建议每块约 500-800 字，相邻块 50-100 字重叠。
2. Metadata：每个 chunk 保留教材名、章节标题、起始页码。
3. Embedding：每个 chunk 转成向量。推荐 sentence-transformers、OpenAI Embedding、BGE。
4. Retrieval：问题转向量，检索 top-5 chunk。
5. Answer：只基于上下文回答，必须引用来源。

引用格式：
- [教材名称, 第 X 章, 第 X 页]

如果找不到答案：
- 回复“当前知识库中未找到相关信息”。

前端要求：
- 问答输入框。
- 回答正文 + 引用来源列表。
- 每条引用显示教材名、章节、页码、相关度分数。
- 点击引用可展开原文 chunk。
- 显示索引状态：已索引 X 本教材，共 X 个知识块。

API 参考：
- POST /api/rag/index
- POST /api/rag/query
- GET /api/rag/status

### 3.6 Agent 架构设计与说明文档

必须提交：
- docs/Agent架构说明.md

官方强调：不看 Agent 数量，看设计决策合理性和论证深度。单 Agent 可以高分，多 Agent 也可以，但必须说明为什么。

文档必须包含：
- 架构总览：有几个 Agent 或模块，各自负责什么。
- 设计决策论证：为什么这样设计，解决什么问题。
- 数据流与调用链路：上传教材 -> 构建图谱 -> 整合 -> 问答。
- 关键接口输入输出。
- 取舍与权衡：放弃了哪些方案，为什么。
- 已知局限与未来改进。

建议有 Mermaid 架构图。

### 3.7 整合建议与多轮对话

要求：
- 对每一项整合决策给出理由。
- 提供教师聊天界面。
- 教师可以用自然语言修改整合方案。

示例：
- “为什么把《生理学》里的炎症和《病理学》里的炎症反应合并？”
- “我觉得免疫应答不应该被删除，请保留。”
- “把抗原和免疫原分开，它们不是同一个概念。”

验收点：
- 教师能通过对话修改至少一项整合决策。
- 修改后在图谱或整合结果中反映变化。
- 至少在同一会话中保留上下文。

### 3.8 Web 交互界面

系统必须是 Web 应用，浏览器可访问。

建议布局：
- 左侧：教材管理区，上传、列表、状态。
- 中间：知识图谱可视化区，最大面积。
- 右侧：功能面板，Tab 切换：整合操作 / RAG 问答 / 对话 / 报告。

要求：
- SPA 单页应用。
- 1920x1080 下正常显示。
- 所有功能模块可操作。

### 3.9 整合报告

必须以赛方 7 本教材为例，输出完整整合报告：
- report/整合报告.md

报告内容：
- 整合概览：原始教材数、总字数、整合后字数、压缩比。
- 整合决策摘要：merge / keep / remove 数量。
- 知识图谱统计：整合前节点数、整合后节点数、关系数变化。
- 重点整合案例：列 3-5 个典型决策，说明原因。
- 教学完整性说明：整合后是否有知识缺口，如何保证教学逻辑链路不断裂。

### 3.10 开发文档

必须具备：
- README.md：项目简介、环境依赖、安装、配置、启动、使用说明。
- docs/需求分析.md：子问题分解、知识点粒度、重复判定、教学连贯性、压缩比、RAG 分块依据。
- docs/系统设计.md：架构图、数据流、技术选型、API 一览。
- docs/Agent架构说明.md：核心评分文档。
- report/整合报告.md：整合结果。

## 10. 建议技术栈

优先选择五小时内稳定可交付的组合。

前端：
- React + Vite + TypeScript。
- Cytoscape.js 或 ECharts 做知识图谱。
- 普通 CSS 或轻量样式，不追复杂 UI 库。

后端：
- FastAPI。
- Python 数据处理。
- PyMuPDF 解析 PDF。
- Markdown/TXT 直接解析。
- python-docx 作为可选 DOCX 支持。

存储：
- 本地 JSON 文件做第一版，结构简单、便于调试。
- SQLite 可作为后续增强。
- 向量索引第一版可用轻量内存索引或简化相似度；有时间再接 FAISS/Chroma。

LLM/Embedding：
- 抽取、对齐、回答统一通过可配置 LLM Provider。
- 没有 API key 时，系统保留规则 fallback，保证演示不崩。
- Embedding 优先留接口，第一版可用关键词/Jaccard/TF-IDF 近似，后续升级。

Agent 架构：
- 用“模块化单 Agent 编排”实现，用文档论证为 Agent 化架构。
- 不硬上复杂 LangGraph/CrewAI，避免五小时内工程风险过大。

## 11. Agent/模块设计

推荐架构：

```text
Orchestrator Agent
  -> Parser Module：教材解析、章节识别、字数统计
  -> Knowledge Extractor：知识点与关系抽取
  -> Alignment Engine：跨教材同义对齐
  -> Compression Planner：主干保留、细节降级、压缩比控制
  -> Graph Builder：节点、边、来源、频次、可视化数据
  -> RAG QA Agent：chunk、检索、引用、回答
  -> Teacher Feedback Agent：解释决策、接受修改、更新图谱
  -> Report Writer：整合报告与架构说明
```

为什么这样设计：
- 五小时内比多 Agent 更稳。
- 每个模块职责清晰，便于写架构说明。
- 对评委可以解释为“单 Orchestrator + 专用能力模块”的 Agent 架构。
- 后续可平滑拆成多 Agent。

## 13. 实现时的关键取舍

必须保证：
- 能演示完整流程。
- 数据有来源可追溯。
- 压缩比可解释。
- 图谱可交互。
- RAG 回答带引用。
- 文档齐全。

可以牺牲：
- 高精度真实 embedding。
- 完全自动的深度语义对齐。
- 很漂亮的 UI。
- 多 Agent 框架本体。
- DOCX/Excel。
- 复杂 benchmark。

最重要的一句话：
先做“可解释、可追溯、可压缩”的整合闭环，再做智能程度提升。
