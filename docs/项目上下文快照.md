## 1. 当前目标

比赛项目：学科知识整合智能体。

核心产品目标：
- 提高学生学习效率。
- 提高教师备课效率。
- 帮助教学管理者做课程整合，重点是课时压缩。

产品三大块：
- 图谱（前端 1）：知识图谱展示、节点详情、跨教材来源和整合状态。
- 问答（前端 2）：基于整合知识库的 RAG 问答，必须带来源引用。
- 整合索引（后端）：教材解析、知识抽取、图谱构建、跨教材对齐、压缩决策、RAG 索引、报告。

## 2. 核心产品原则

精简不是简单删除，而是抓主干、降细节：
- 主干保留：定义、关键关系、学习顺序、必要方法、核心机制。
- 细节降级：具体案例、重复解释、长背景只保留一句关键词和来源索引。
- 删除可追溯：remove 的内容进入索引或引用，不让教学完整性被质疑。

评审策略：
- 赛题条目多、现场评审短，初筛很可能由 AI 工具辅助。
- 因此项目必须机器可审计：模块名、API、文档、脚本、报告都显式对应评分点。
- P1 先确保闭环可跑，再补视觉美工，用于冲刺人工评委印象分和创新分。

## 7. 已定架构决策

Agent 架构：
- 采用模块化单 Orchestrator Agent。
- 不拆复杂多进程多 Agent，避免 5 小时赛程中调试和部署风险。
- 模块职责清楚即可满足官方“设计合理性”评分。

模块映射：
- Parser Module：教材解析，B1。
- Knowledge Extractor：知识点与关系抽取，B2。
- Graph Builder：图谱 JSON 和可视化，B2/B3/C。
- Alignment Engine：跨教材同义对齐，B4。
- Compression Planner：merge/keep/remove 和 30% 压缩，B4。
- RAG QA Agent：带引用问答，B5。
- Teacher Feedback Agent：教师反馈修改决策，B6。
- Report Writer：整合报告，A4。

“问答（前端 2）”拆成两个入口：

Case A 的查询优先级：
- 第一优先级：Case B 已整合资料，包括 `integrated_corpus_demo.json`、当前 session 中的 `decision_overrides` 和整合决策文本。
- 第二优先级：7 本教材原文 chunk，来自 `data/processed/textbooks.json`，字段包括教材名、章节段、页码、原文片段。
- 命中时提示：`正在查找 agent 资料库 -> 已命中 agent 已整合资料`。
- 教材命中时提示：`正在查找 agent 资料库 -> 本地整合资料不足；正在检索教材原文 -> 已命中教材 RAG`。
- 未命中或证据不足时提示：`正在查找 agent 资料库 -> 本地资料不足；正在联网检索`。
- 重要修正：本地资料库检索不能只因为出现局部词就直接回答。例如“甲状腺结节的典型症状是什么”不能用“甲状腺结构/功能”的整合资料硬答，必须转入 LLM/联网检索路径。
- 当前已支持真实 LLM 调用入口；但联网能力取决于用户配置的模型/API 是否支持外部检索。如果 API 不支持联网，提示词要求 LLM 明确说明，不得伪造网页来源。
- Case A 输出修正：LLM 如果返回 JSON 字符串，前端必须解析 `answer / web_sources / local_kb_status / follow_up_suggestion` 后再渲染，不能直接显示原始 JSON 或字面量 `\n`。检索过程中也要用实时提示提前反馈：`正在检索本地资料...`、`本地资料不足；正在联网检索...`。

Case B 优先目标不是做泛聊天，而是服务整合方案迭代：
- 解释：回答“为什么这样合并/保留/降级”，必须引用 `decision_id`、来源教材、理由类型和证据页段。
- 修改：支持教师自然语言修改至少一条整合决策，例如保留某概念、拆分某节点、降低案例权重、补充图表索引。
- 记忆：同一会话内保留上下文，后续追问可以沿用上一个决策对象。
- 反馈落地：修改后的决策要反映到整合决策列表和图谱数据中，不能只停留在聊天文本。
- 无 key fallback：没有 API key 时，先用规则意图识别完成 demo；有 API key 时，用 `docs/LLM整合提示词设计.md` 中的约束提示词调用 LLM。
- Prompt 优先级：教师写入要求 > Agent 默认整合策略。默认策略只在教师没有明确说明时兜底；如果教师要求覆盖默认策略，需要在决策中记录 `teacher_override_note` 或同等说明。
